---

1. Goal

Define the Web Information Architecture and Navigation Architecture based on the P1 Product/UX baseline and P2.1 Information Architecture Foundation.

The goal is to establish a clear, scalable, role-aware Web structure without mapping backend entities directly into navigation items.

---

2. Core Principles

2.1 Navigation is User/Job/Context Driven

Navigation must reflect:

- user goals
- operational tasks
- spatial context
- work context
- workflow continuity

and must not mirror database tables or backend routes.

2.2 Project is a Major Operational Context

A Project provides context for:

- spatial areas
- field operations
- incidents
- patrols
- fire
- grazing
- actions
- restoration
- monitoring
- forms
- attachments
- reports

The currently selected Project must remain visible and understandable across relevant screens.

2.3 Map is a Cross-Domain Workspace

Map is not merely another CRUD page.

The Map Workspace can provide:

- layers
- spatial filters
- feature selection
- feature inspection
- spatial context
- timeline
- operational overlays
- analytical results

2.4 Navigation Explosion Must Be Avoided

Backend objects must not automatically become primary navigation items.

The following should not become a flat primary menu:

Field Visits
Incidents
Violations
Fire Events
Grazing Events
Patrols
Actions
Attachments
Form Definitions
Form Versions
Form Submissions
Audit Logs
...

Instead, related concepts should be organized into meaningful workspaces.

---

3. Web Product Mental Model

The Web application should behave as a:

Spatial + Operational Command Center

The primary question is not:

«"Which database object do I want?"»

The primary question is:

«"What do I need to understand, investigate, decide, or act on?"»

5. Navigation Structure

5.1 Overview

Purpose:

Provide an operational starting point rather than a generic KPI dashboard.

Possible content:

- active priorities
- recent incidents
- pending actions
- overdue verification
- field activity
- sync/data health indicators
- spatial highlights
- recent operational changes

Primary mental model:

"What needs my attention?"

---

5.2 Map

Purpose:

Provide the primary spatial investigation workspace.

Core capabilities:

Map
├── Layers
├── Search
├── Filters
├── Selection
├── Feature Inspector
├── Timeline
├── Spatial Context
└── Analysis / Results

The Map Workspace should support moving between:

Map → Feature → Detail
Map → Incident → Action
Map → Restoration Site → Monitoring
Map → Field Activity → Visit
Map → Analysis → Result

---

5.3 Operations

Operations groups operational events and field activities.

Conceptual structure:

Operations
├── Incidents
├── Violations
├── Fire
├── Grazing
├── Patrols
└── Field Activity

The grouping is intentional.

These are not necessarily separate top-level navigation destinations.

Primary mental model:

"What is happening operationally?"

---

5.4 Projects

Purpose:

Manage and enter project-specific operational context.

Project Workspace may contain:

Project
├── Overview
├── Areas
├── Field Activity
├── Incidents
├── Actions
├── Restoration
├── Monitoring
├── Forms
├── Map Context
└── Reports

Project pages should preserve project context.

---

5.5 Actions

Purpose:

Provide a cross-domain action and follow-up workspace.

Actions may originate from:

- incidents
- violations
- patrol observations
- fire events
- grazing events
- restoration findings
- monitoring findings

Core lifecycle:

Issue
  ↓
Action
  ↓
Execution
  ↓
Evidence
  ↓
Verification

Primary mental model:

"What work must be done, and what still needs verification?"

---

5.6 Restoration

Purpose:

Provide a lifecycle-oriented workspace for restoration operations.

Possible structure:

Restoration
├── Sites
├── Planting
├── Maintenance
└── History

The structure should emphasize lifecycle continuity rather than exposing backend tables.

---

5.7 Monitoring

Purpose:

Track monitoring processes and changes over time.

Possible structure:

Monitoring
├── Active Monitoring
├── Monitoring History
├── Status / Findings
└── Spatial & Temporal View

Monitoring should connect naturally with:

Restoration Site
→ Planting
→ Monitoring
→ Finding
→ Action
→ Verification

---

5.8 Reports

Purpose:

Provide operational and analytical reporting.

Initial scope:

- operational reports
- incident reports
- action status
- restoration status
- monitoring summaries
- spatial summaries

Reports should be connected to the underlying operational context.

A report should not become a disconnected BI experience.

---

5.9 Administration

Administration is intended for configuration and system management rather than daily field operations.

Possible structure:

Administration
├── Users
├── Roles
├── Organizations
├── Projects / Configuration
├── Forms / Configuration
└── System Settings

Technical/internal entities such as audit logs, sync internals, etc. should not automatically appear in primary navigation.

---

7. Project Context Switcher

Project Context is a first-class product concept.

The user should be able to:

Select Project
      ↓
All contextual screens reflect selected Project

The selected Project should be visibly represented in the application shell.

Navigation must distinguish:

Global Context
vs.
Project Context

8. Global vs Contextual Navigation

Global

Examples:

- Overview
- Map
- Search
- Notifications
- Profile
- Administration

Contextual

Examples:

- Project Areas
- Project Field Activity
- Project Incidents
- Project Actions
- Project Restoration
- Project Monitoring

Contextual navigation must never make the user lose awareness of the current Project.

It must not create completely different applications for different roles.

Role-aware visibility
+
Role-aware actions
+
Progressive disclosure

Operations

Actions

Operational Supervisor

Emphasis:

Operations
Map

Reports

GIS Specialist

Emphasis:

Map
Projects

Monitoring
Reports

Manager

Emphasis:

Overview
Map
Operations
Reports

Administrator

Emphasis:

Roles
Forms

Role-based visibility must not destroy discoverability or workflow continuity.

12. Primary Object Actions

Navigation and detail pages should emphasize the next useful action.

Examples:

Field Visit      → Continue
Incident         → Review / Act
Action           → Execute / Verify
Restoration Site → Monitor
Feature          → Inspect

The UI should not force users to navigate through multiple pages merely to perform a common operational action.

---

13. Search

Search is a cross-cutting capability.

It should eventually support searching across relevant objects such as:

Projects
Features
Field Visits
Incidents
Actions
Restoration Sites
Monitoring Records

Search results should preserve context and support deep linking.

Example:

Search
  ↓
Incident
  ↓
Incident Detail
  ↓
Map Context
  ↓
Related Action

---

14. Notifications

Notifications are cross-cutting and separate from alerts.

Examples:

Notification

Your assigned action was updated.

Alert

A high-priority incident requires attention.

The distinction should remain explicit in future UX implementation.

---

15. Deep Linking

Web navigation must support deep links.

A deep link should preserve:

User
Project
Workspace
Object
Spatial Context

Examples conceptually:

Project → Incident → Map Context
Project → Restoration Site → Monitoring
Action → Evidence → Verification
Feature → Related Records

Deep linking is important for notifications, search results, reports, and collaboration.

---

16. Responsive Strategy

Web is Windows/Desktop-primary.

The initial design target is:

Desktop
   ↓
Large-screen operational workflows
   ↓
Responsive adaptation

The Web experience should not become a stretched version of the mobile application.

Desktop can intentionally support:

- multiple panels
- simultaneous map + list + inspector
- dense operational information
- keyboard interaction
- larger analytical workspaces

---

17. Navigation Anti-Patterns

The following are explicitly rejected:

Anti-pattern 1

Every backend table becomes a menu item.

Anti-pattern 2

Every relationship becomes a standalone page.

Anti-pattern 3

One identical navigation is forced on every persona.

Anti-pattern 4

Map is treated as a simple standalone CRUD page.

Anti-pattern 5

Sync is hidden as a generic technical setting.

Anti-pattern 6

Users lose Project context while navigating.

Anti-pattern 7

Operational actions require excessive navigation depth.

19. P2.2 Decision Gate

Decisions accepted

1. Web application uses a workspace-oriented IA.
2. Primary navigation is user/job/context driven.
3. Project is a major operational context.
4. Map is a cross-domain spatial workspace.
5. Operations groups related operational concepts.
6. Actions are cross-domain and lifecycle-oriented.
7. Object detail follows a consistent workspace pattern.
8. Search and notifications are cross-cutting.
9. Navigation is role-aware but based on one shared IA.
10. Web is Desktop/Windows-primary and fundamentally different from Mobile IA.
11. Backend entities are not mapped 1:1 to navigation items.

Explicitly deferred

- final visual design
- typography
- colors
- design tokens
- component library
- exact responsive breakpoints
- exact map engine
- implementation framework details
- accessibility audit
- usability testing
- final navigation icons
- advanced GIS analysis UI

These belong to later Product/UI/Architecture stages.

---

20. Safety / Scope Boundary

P2.2 is a Product / UX / Information Architecture decision Gate.

No changes are made to:

- Backend
- API
- Database
- PostgreSQL
- PostGIS
- ORM
- migrations
- authentication
- RBAC implementation

Therefore:

Backend Mutation = NONE
Schema Delta = NONE
Migration = NONE
