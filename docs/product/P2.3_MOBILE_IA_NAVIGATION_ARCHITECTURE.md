1. Goal

Define the Mobile Information Architecture and Navigation Architecture based on the P1 Product/UX baseline and the P2.1 Information Architecture Foundation.

The mobile architecture must support field-first, action-first, location-first, and offline-first operation.

Mobile must not be implemented as a smaller version of the Web application.

---

2. Mobile Product Mental Model

The primary mobile mental model is:

My Work

The user should primarily think:

«What do I need to do now?»

rather than:

«Which database object do I want to open?»

The mobile experience should reduce navigation depth and unnecessary typing while preserving operational context.

---

3. Mobile Design Priorities

The Mobile IA prioritizes:

1. Current work
2. Location
3. Field activity
4. Drafts
5. Offline state
6. Sync state
7. Attachments / evidence
8. Fast operational actions

The architecture must support:

LOCATE
  ↓
OBSERVE
  ↓
CAPTURE
  ↓
SAVE
  ↓
SYNC

---

4. Core Mobile Navigation

The initial Mobile navigation baseline is:

Home
Map
My Work
Drafts
Sync
Profile

This structure is intentionally smaller than the Web navigation.

---

5. Home

Home is the field user's operational starting point.

It should answer:

«What should I do next?»

Possible content:

Home
├── Current Project
├── Today's Work
├── Assigned Tasks
├── Recent Drafts
├── Sync Status
├── Location / GPS Status
└── Quick Actions

The Home screen should prioritize action over information volume.

---

6. Home Quick Actions

Quick Actions may provide direct access to common field operations.

Examples:

Start Field Visit
Create Incident
Capture Observation
Open Map
Continue Draft
Record Patrol Activity
Create Action Evidence

Quick Actions should be role-aware and context-aware.

They should not expose every backend capability.

---

7. Map

Map is a primary mobile workspace.

It supports:

Map
├── Current Location
├── Project Context
├── Layers
├── Features
├── Search
├── Spatial Selection
├── Feature Inspector
└── Navigation to Nearby Work

The mobile map should prioritize field usability.

Important interactions include:

My Location
→ Nearby Feature
→ Inspect
→ Capture
→ Save

---

8. My Work

My Work is the central operational workspace for mobile.

Conceptual structure:

My Work
├── Today
├── Assigned
├── In Progress
├── Completed
└── Follow-up

Potential work items include:

- Field Visits
- Tasks
- Assigned Actions
- Follow-up activities
- Monitoring activities
- Other role-relevant field work

The exact object types must remain flexible.

---

9. Work Item Model

A work item should expose the next useful action.

Examples:

Field Visit
→ Continue

Assigned Action
→ Execute

Incident Follow-up
→ Review

Monitoring Task
→ Capture

Verification Task
→ Verify

The mobile application should minimize the number of steps between opening work and performing the next action.

---

10. Drafts

Drafts are a first-class operational concept.

Drafts may contain:

- partially completed Field Visits
- incomplete Forms
- unsynced Incidents
- incomplete Actions
- captured Attachments
- pending field observations

The user must be able to resume work without reconstructing context.

Primary mental model:

Draft
→ Continue

not:

Draft
→ Rebuild

---

11. Offline Mode

Offline is an operating mode.

It must never be represented merely as an error condition.

Conceptually:

ONLINE
  ↕
OFFLINE
  ↕
LIMITED CONNECTIVITY

The user should understand what can still be done in each state.

---

12. Offline Capability Model

The mobile IA must preserve access to essential offline workflows:

Field Visit
Forms
Drafts
GNSS
Photos
Attachments
Incident
Patrol
Fire
Grazing
Restoration
Monitoring

The exact offline implementation belongs to Architecture/Engineering stages.

This Gate establishes the product requirement, not the storage technology.

---

13. Sync

Sync must be visible as an operational capability.

Primary states include:

Saved Locally
↓
Waiting for Sync
↓
Uploading
↓
Uploaded
↓
Verified

Failure states must be recoverable.

Example:

Sync Failed
   ↓
Retry

The user must not lose local work because synchronization failed.

---

14. Sync Center

The Sync destination may provide:

Sync
├── Pending
├── Uploading
├── Completed
├── Failed
└── Retry

The screen should answer:

What is waiting?
What is uploading?
What failed?
What was completed?

Technical implementation remains outside this Gate.

---

15. Attachments / Evidence

Attachments are cross-cutting evidence objects.

The user experience should support:

Capture
→ Store Locally
→ Associate with Work
→ Sync
→ Verify

Typical field evidence may include:

- photographs
- documents
- location context
- other supported media

Attachment management should normally be contextual rather than a primary navigation destination.

---

16. GNSS / Location

Location is a fundamental part of field interaction.

The mobile architecture should provide visible awareness of:

Location Available
Location Uncertain
Searching for Location
Location Unavailable

Where relevant, the user should be able to understand:

- current position
- accuracy
- GPS availability
- location-related restrictions

The exact GNSS UI is deferred to later UX/UI design.

---

17. Project Context

Project remains a major context on mobile.

The user should always understand:

Which Project am I working in?

Context should persist across:

Home
Map
My Work
Drafts
Forms
Attachments
Actions

Project switching must be explicit.

---

18. Profile

Profile is intentionally lightweight.

Possible content:

Profile
├── Account
├── Preferences
├── Language
├── Theme
└── About

Technical system controls should not be unnecessarily exposed here.

Sync should remain accessible as a first-class operational capability.

20. Bottom Navigation Strategy

The navigation should expose the most frequent field destinations.

Baseline:

Home
Map
My Work
Drafts
More

Within "More":

Sync
Profile
Other secondary destinations

Sync may be promoted visually when pending or failed items require attention.

This is preferable to permanently allocating too many primary navigation slots to technical functions.

---

21. Field Session Continuity

The mobile application must support continuity across interruptions.

Examples:

Start Visit
   ↓
Capture Observation
   ↓
Take Photo
   ↓
Leave App
   ↓
Return
   ↓
Continue Visit

The user should return to the relevant operational context rather than the generic Home screen whenever practical.

---

22. One-Hand and Outdoor Constraints

The IA must accommodate:

- one-handed interaction
- high sunlight
- limited attention
- gloves
- movement
- intermittent connectivity
- GPS uncertainty
- long field sessions
- minimum typing

These requirements affect later component and interaction design.

---

23. Progressive Disclosure

Mobile should reveal complexity progressively.

Example:

Simple Capture
    ↓
More Details
    ↓
Advanced / Optional Information

Required information should appear before optional information.

Technical metadata should remain out of the primary field flow unless operationally necessary.

---

24. Error and Recovery Model

Errors should be recoverable.

Examples:

GPS unavailable
→ Continue with limited location state

Network unavailable
→ Save locally

Upload failed
→ Retry later

Form incomplete
→ Save Draft

Attachment upload failed
→ Retry

Errors must not unnecessarily interrupt field work.

---

25. Notifications

Mobile notifications should support operational continuity.

Potential examples:

New assignment
Action updated
Verification required
Sync issue
Important operational alert

Notifications should deep-link into the relevant object or workspace.

---

30. Mobile Workflow Depth

Common workflows should be intentionally shallow.

For example:

Home
→ My Work
→ Field Visit
→ Continue

or:

Map
→ Feature
→ Capture
→ Save

Avoid unnecessary chains such as:

Home
→ Module
→ List
→ Category
→ Object
→ Sub-object
→ Action

31. Navigation Anti-Patterns

The following are rejected:

Anti-pattern 1

Copying the Web sidebar into mobile.

Anti-pattern 2

Creating one navigation item for every backend entity.

Anti-pattern 3

Hiding Sync inside Settings.

Anti-pattern 4

Treating Offline as an error-only screen.

Anti-pattern 5

Forcing users to recreate interrupted work.

Anti-pattern 6

Requiring unnecessary typing during field work.

Anti-pattern 7

Making Map a decorative screen instead of a field workspace.

Anti-pattern 8

Losing Project context during field workflows.

33. P2.3 Decision Gate

Decisions accepted

1. Mobile uses a field-first Information Architecture.
2. Mobile mental model is My Work.
3. Home focuses on the next useful action.
4. Map is a primary field workspace.
5. My Work is the central operational workspace.
6. Drafts are first-class.
7. Offline is an operating mode, not an error state.
8. Sync is a visible operational capability.
9. Attachments are contextual evidence objects.
10. GNSS/location awareness is fundamental.
11. Project context persists across major mobile workflows.
12. Mobile navigation is intentionally different from Web navigation.
13. One shared IA supports role-aware experiences.
14. Common field workflows should remain shallow.
15. Error states must provide recovery paths.

35. Safety / Scope Boundary

P2.3 is a Product / UX / Information Architecture Gate.

No changes are made to:

- Backend
- API
- Database
- PostgreSQL
- PostGIS
- ORM
- migrations
- authentication
- RBAC implementation

Therefore:

Backend Mutation = NONE
Database Mutation = NONE
Schema Delta = NONE
Migration = NONE
