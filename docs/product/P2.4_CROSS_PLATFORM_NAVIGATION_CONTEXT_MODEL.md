1. Goal

Define a shared Cross-Platform Navigation and Context Model for GeoField Web and Mobile.

The purpose is to establish one coherent Product Navigation Model while preserving platform-specific experiences.

The result must support:

One Product
+
Shared Domain
+
Shared API
+
Shared Context
+
Platform-specific UX

---

2. Core Principle

GeoField has one product model, but two contextual experiences:

WEB
Spatial + Operational Command Center

MOBILE
Field-first + Offline-first + Action-first + Location-first

The platforms must share meaning, context, permissions, and workflow semantics.

They must not be forced to share identical navigation or interaction patterns.

4. Context Hierarchy

The application must preserve context across navigation.

The conceptual hierarchy is:

User
  ↓
Organization
  ↓
Project
  ↓
Workspace
  ↓
Object
  ↓
Action / Evidence / Related Record

Not every level must appear explicitly in every screen.

The purpose is to preserve meaning, not to increase UI complexity.

---

5. Context Types

5.1 Identity Context

Represents:

- authenticated user
- organization
- permissions
- persona-related capabilities

The application must know:

Who am I?
What can I do?

---

5.2 Project Context

Represents:

Which Project am I currently working in?

Project context should influence relevant:

- data
- map layers
- field activity
- incidents
- actions
- restoration
- monitoring
- forms
- reports

Project switching must be explicit.

---

5.3 Workspace Context

Represents the user's current area of work.

Examples:

Map Workspace
Operations Workspace
Project Workspace
Action Workspace
Restoration Workspace
Monitoring Workspace

---

5.4 Object Context

Represents the specific object currently being viewed or edited.

Examples:

Field Visit
Incident
Action
Feature
Restoration Site
Monitoring Record

---

5.5 Spatial Context

Represents the geographic context associated with the current work.

Examples:

Current Location
Selected Feature
Project Area
Incident Location
Restoration Site
Monitoring Location

Spatial context should be preserved where meaningful.

---

6. Context Persistence

Context should persist across transitions where operationally meaningful.

Example:

Project A
   ↓
Map
   ↓
Incident #123
   ↓
Action
   ↓
Verification

The user should not unexpectedly return to a global or unrelated context.

---

7. Context Reset Rules

Not all transitions preserve every context.

Context may be intentionally reset when:

- the user changes Project
- the user explicitly exits a workspace
- a global search is launched
- the user logs out
- a permission boundary is crossed

Reset behavior should be intentional and understandable.

→ Incident

Example:

16. Back Navigation

Back navigation must preserve workflow continuity.

The semantic model is:

Current Context
→ Previous Relevant Context

not necessarily:

Current Screen
→ Previous URL

The exact behavior depends on platform conventions.

Web may use:

- browser history
- workspace routing
- preserved panels

Mobile may use:

- platform back behavior
- navigation stack
- restored work state

---

17. Cross-Platform Object Identity

Objects must have consistent identity across platforms.

For example:

Incident ID = same object
Project ID = same object
Action ID = same object
Restoration Site ID = same object

Web and Mobile must not create incompatible conceptual object identities.

---

18. Shared Workflow Semantics

A workflow should have the same meaning on both platforms.

Example:

Issue
↓
Action
↓
Execution
↓
Evidence
↓
Verification

Web may provide a rich multi-panel workflow.

Mobile may provide a focused step-by-step flow.

The semantics remain identical.

---

19. Offline Context Rules

Mobile introduces local state.

Therefore the context model must distinguish:

Server Context
vs.
Local Context

Example:

Project A
→ Draft Field Visit
→ Saved Locally
→ Waiting for Sync

The user must retain enough context to resume the draft even without network connectivity.

---

20. Sync Context

Sync status must be associated with the relevant object/workflow.

Example:

Incident #123
Status:
Saved Locally
Waiting for Sync

rather than only showing a generic technical message.

Where possible, the user should know:

What?
Where?
Why?
What can I do?

---

21. Attachment Context

Attachments must retain association with their parent operational object.

Conceptually:

Project
→ Incident
→ Evidence
→ Attachment

or:

Project
→ Field Visit
→ Attachment

The attachment experience should preserve the parent context during capture, review, sync, and verification.

---

22. Form Context

Forms must operate inside a meaningful operational context.

Examples:

Field Visit
→ Form
→ Submission

or:

Incident
→ Form
→ Submission

Dynamic Forms are runtime-driven and must not require navigation structures hard-coded for individual form definitions.

---

23. Role Context

Role-aware behavior must operate as a layer over shared navigation.

Conceptually:

Shared Navigation Model
        +
Permission Model
        +
Persona / Job Priorities
        ↓
Role-aware Presentation

This must not result in unrelated applications for different roles.

---

24. Context-Aware Primary Actions

Primary actions should depend on the current context.

Examples:

Field Visit
→ Continue

Incident
→ Review / Act

Action
→ Execute / Verify

Restoration Site
→ Monitor

Feature
→ Inspect / Capture

Context must influence action priority.

---

25. Navigation Visibility vs Permission

The product must distinguish:

Not relevant
vs.
Not permitted
vs.
Not available offline
vs.
Temporarily unavailable

A hidden feature should not be interpreted automatically as a permission denial.

The exact permission-to-UI mapping belongs to later UX and implementation stages.

---

26. Global Search / Contextual Search

Search may operate at multiple scopes.

Global Search

Across the user's accessible product data.

Project Search

Limited to the active Project.

Workspace Search

Limited to the current operational workspace.

The UI must communicate the active search scope.

30. Context Loss Anti-Patterns

The following are rejected:

Anti-pattern 1

Opening a record without showing its Project context.

Anti-pattern 2

Returning the user to a generic Home after every action.

Anti-pattern 3

Losing spatial context when opening Feature details.

Anti-pattern 4

Opening a Draft without restoring its associated work.

Anti-pattern 5

Treating Sync as detached from the affected object.

Anti-pattern 6

Creating different object semantics between Web and Mobile.

31. Information Architecture Governance

Future frontend features should be evaluated against this model.

A proposed feature must answer:

Which user job?
Which context?
Which workspace?
Which object?
Which primary action?
Web, Mobile, or both?
Does it preserve shared semantics?

A feature should not automatically introduce a new top-level navigation item.

33. Accessibility and Context Clarity

Context must be clear through more than color alone.

Important contextual information should remain understandable through:

- visible labels
- hierarchy
- status indicators
- text
- meaningful icons
- consistent positioning

The detailed accessibility audit is deferred.

---

34. Localization Boundary

The navigation model must support localization.

Persian is the current UI language, but the Product Model must not be tied to one language.

Conceptually:

Product Concept
     ↓
Localized Label

not:

Hard-coded Product Concept

RTL/LTR behavior is a presentation concern, not a change to underlying Product semantics.

---

35. Internationalization Boundary

The product must remain country-neutral.

Country-specific behavior should come from:

- configuration
- localization
- organization settings
- deployment settings
- data

rather than being embedded into the navigation architecture.

37. P2.4 Decision Gate

Decisions accepted

1. Web and Mobile share one Product Model.
2. Web and Mobile maintain platform-specific UX.
3. Project is a persistent major context.
4. Workspace is distinct from navigation destination.
5. Object identity is shared across platforms.
6. Spatial context is preserved where meaningful.
7. Search and notifications participate in context restoration.
8. Deep links must restore relevant context.
9. Offline drafts retain sufficient local context for continuation.
10. Sync state remains associated with operational objects.
11. Attachments preserve parent context.
12. Forms operate within operational context.
13. Role-aware UI is layered over shared navigation semantics.
14. Navigation items are not generated directly from backend entities.
15. Localization and country-specific behavior remain configuration/data concerns.
16. Routing and state-management technologies are deferred to later architecture stages.
