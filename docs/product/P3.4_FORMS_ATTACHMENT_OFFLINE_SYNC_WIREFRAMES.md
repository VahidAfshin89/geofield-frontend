---

1. Goal

The goal of P3.4 is to define the wireframe and interaction architecture for the cross-cutting data workflows that connect:

- Dynamic Forms
- Form State
- Attachments
- Local Save
- Drafts
- Offline Operation
- Sync
- Upload
- Verification
- Error Recovery

These capabilities are central to GeoField because the Product must remain reliable under field conditions with intermittent or unavailable network connectivity.

P3.4 translates the existing Backend capabilities and the approved UX principles from P1, P2, P3.1, P3.2, and P3.3 into a coherent user experience.

71. Anti-Patterns

The following are rejected:

Anti-pattern 1

Treating every Form Save as a server upload.

Anti-pattern 2

Showing only "Saved" without identifying local/server status.

Anti-pattern 3

Deleting local evidence after a failed upload.

Anti-pattern 4

Hiding failed sync items.

Anti-pattern 5

Forcing the user to restart a Draft.

Anti-pattern 6

Blocking field work because the network is unavailable.

Anti-pattern 7

Treating Upload and Verification as the same state.

Anti-pattern 8

Exposing technical queue terminology to field users.

Anti-pattern 9

Creating different state meanings on Web and Mobile.

83. P3.4 Decision Gate

The following decisions are accepted:

1. Dynamic Forms remain runtime-driven.
2. Forms remain inside operational context.
3. Local Save is distinct from Server Upload.
4. Drafts are first-class.
5. Offline is an operating mode.
6. Sync is a visible operational capability.
7. Attachments are contextual Evidence Objects.
8. Attachment lifecycle is visible where useful.
9. Upload and Verification are distinct.
10. Failed uploads must be recoverable.
11. Local evidence must remain protected during upload failure.
12. Resume must restore meaningful context.
13. Form Version context must be preserved.
14. Web and Mobile share state semantics.
15. Mobile prioritizes capture and continuity.
16. Web prioritizes review and operational visibility.
