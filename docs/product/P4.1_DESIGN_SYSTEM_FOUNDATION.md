---

1. Goal

The goal of P4.1 is to establish the foundational principles and architecture of the GeoField Design System.

P4 begins after the formal completion of:

- P1 — Product UX Discovery
- P2 — Information Architecture
- P3 — UX Flows, Wireframes & Interaction Architecture

P3 established:

- User Jobs
- Context
- Navigation
- Workspaces
- Objects
- Primary Actions
- Workflows
- States
- Evidence
- Verification
- Mobile/Web UX differences
- Cross-platform semantics

P4.1 now establishes the visual and component-system foundation required to translate that UX architecture into a coherent interface.

P4.1 is therefore a Design System Foundation Gate, not a final UI implementation Gate.

---

2. P4 Boundary

The P4 phase is explicitly divided from P3.

P3
Behavior
+
Structure
+

+

        ↓

P4

+

P4 must not redefine the core Product UX architecture established in P3 unless new evidence demonstrates that a correction is necessary.

3. Design System Objective

The GeoField Design System must provide a common visual language for:

- Mobile
- Web
- Light Mode
- Dark Mode
- RTL
- LTR
- Operational Interfaces
- Spatial Interfaces
- Field Workflows
- Analytical Workspaces

The Design System must create visual consistency without forcing identical layouts across platforms.

---

4. Core Design System Principle

The foundational principle is:

Shared Visual Language
≠
Identical UI

Web and Mobile may differ in:

- Layout
- Density
- Navigation
- Input Method
- Panel Structure
- Interaction Pattern
- Screen Composition

while remaining visually and semantically part of one GeoField Product.

6. Visual Design Principles

The Design System follows the following principles.

6.1 Clarity Over Decoration

Visual hierarchy must help users understand:

- What is happening
- What is important
- What requires attention
- What can be done next

Decorative elements must not compete with operational content.

6.2 Context Before Complexity

Visual hierarchy should continuously reinforce:

Project
↓
Workspace
↓
Object
↓
Action
↓
State

6.3 Action Visibility

Primary actions must remain visually identifiable.

Examples:

Field Visit
→ Continue

Incident
→ Review / Act

Action
→ Execute / Verify

Restoration Site
→ Monitor

Feature
→ Inspect

6.4 Data Preservation

The visual system must communicate reliability.

Priority:

Data Preservation
>
Operational Continuity
>
Convenience
>
Visual Effects

6.5 Progressive Disclosure

The interface should reveal:

Essential
↓
More Details
↓
Advanced / Optional

rather than presenting maximum information simultaneously.

8. Design Token Principle

Raw visual values should not be scattered throughout the Product.

The preferred architecture is:

Semantic Token
↓
Component
↓
Pattern
↓
Screen

rather than:

Screen
↓
Arbitrary Color / Size / Radius

This allows future visual refinement without uncontrolled redesign.

12. Spacing Foundation

GeoField requires a consistent spacing system.

Spacing must provide predictable relationships between:

- Sections
- Components
- Labels
- Inputs
- Cards
- List items
- Map controls
- Panels
- Dialog content

A tokenized spacing scale is preferred over arbitrary pixel values.

13. Radius Foundation

Corner radius must communicate hierarchy.

Different radius levels may be used for:

- Small controls
- Inputs
- Cards
- Containers
- Dialogs
- Bottom Sheets

Radius must remain controlled and should not become an ornamental visual signature detached from usability.

18. Accessibility Foundation

Accessibility must be treated as a baseline requirement.

The Design System should account for:

- Sufficient contrast
- Visible focus
- Touch target size
- Text readability
- Clear state communication
- Non-color-only meaning
- Keyboard interaction on Web
- Appropriate motion reduction
- Screen-reader-compatible semantics where applicable

Accessibility validation remains a subsequent detailed task.

---

19. RTL / LTR Foundation

RTL is a first-class design-system requirement.

The system must support:

RTL
LTR

without duplicating the Product's semantic model.

The following must be carefully evaluated:

- Text alignment
- Icon placement
- Navigation direction
- Chevrons
- Back/forward semantics
- Map controls
- Tables
- Form layouts
- Bidirectional text
- Numeric content

Persian is the current primary UI language, while the Product model remains language-independent.

---

20. Localization Foundation

The visual system must remain Localization-ready.

Initial conceptual languages:

fa
en
...

UI labels, component semantics, and product identity must not depend on hard-coded language assumptions.

Text expansion and contraction should be considered during component design.

---

21. Country-Neutrality

The Design System must preserve GeoField's international and country-neutral identity.

Country-specific details belong to:

- Localization
- Configuration
- Organization
- Data
- Administrative Hierarchy

They must not become hard-coded Product branding.

---

22. Light / Dark Mode

The Design System supports:

Light
+
Dark

Dark Mode must not be treated as a simple color inversion.

Semantic roles must remain stable while visual values may differ between themes.

Dark Mode must preserve:

- Hierarchy
- Readability
- State recognition
- Map usability
- Accessibility
- Operational clarity

---

23. Mobile Design Foundation

Mobile is:

Field-first
Action-first
Location-first
Offline-first

The Design System must therefore prioritize:

- Touch-friendly controls
- One-handed operation where possible
- High legibility
- Outdoor use
- Clear primary actions
- Minimal cognitive load
- Strong state visibility
- Offline communication

Mobile must not become a scaled-down version of Web.

---

24. Web Design Foundation

Web is:

Spatial
+
Operational
+
Analytical
+
Information-dense

The Design System must support:

- Multi-panel layouts
- Dense tables
- GIS map workspaces
- Filters
- Inspector panels
- Timeline views
- Operational queues
- Dashboards
- Analytical content

Web must not become a generic administrative dashboard.

---

25. Map UI Foundation

The Map is a workspace.

Map-related components must support:

Layers
Filter
Selection
Inspection
Timeline
Spatial Context
Analysis
Action

Map controls must remain visually subordinate to the main task while remaining discoverable.

The Map Engine itself remains intentionally unfrozen.

---

26. Offline and Sync Visual Language

Offline is an Operating Mode.

The visual system must distinguish:

Online
↕
Limited Connectivity
↕
Offline

Sync states must remain semantically distinct:

Saved Locally
↓
Waiting for Sync
↓
Uploading
↓
Uploaded
↓
Verified

Critical distinction:

Saved Locally
≠
Uploaded
≠
Verified

This distinction must be visually represented consistently.

---

27. Error Visual Language

Errors must communicate:

What happened
+
What is affected
+
What can be done next

Preferred structure:

Problem
↓
Context
↓
Recovery Action

Examples:

Network unavailable
→ Continue Offline

Upload failed
→ Retry

Form incomplete
→ Save Draft

GPS unavailable
→ Retry / Continue with limitation

Error visuals must not imply irreversible data loss when the work is recoverable.

---

28. Empty State Foundation

Empty states must distinguish:

No Data
No Results
Not Yet Created
Unavailable
Not Permitted
Not Available Offline

Empty states should provide contextual next actions where appropriate.

---

29. Loading Foundation

Loading should communicate meaningful progress without unnecessary visual noise.

Different loading patterns may include:

- Inline loading
- Component loading
- Page loading
- Map loading
- Sync progress
- Upload progress
- GNSS acquisition

Skeleton patterns may be used where they improve perceived continuity.

---

30. Motion Foundation

Motion must communicate state.

Potential meaningful uses include:

- Navigation
- Loading
- GPS acquisition
- Saving
- Sync
- Upload
- Success
- Failure
- State transition

Motion must not:

- Delay field workflows
- Obscure information
- Introduce unnecessary distraction
- Become a product requirement for basic operation

---

31. 3D Visual Policy

3D remains:

Selective
Purposeful
Optional

Potential uses include:

- Terrain
- Spatial Context
- Environmental Visualization
- Spatial Storytelling
- Meaningful Map Transitions

Core workflows must remain usable without 3D.

The Design System must therefore not depend on 3D rendering.

---

32. Evidence Visual Language

Attachments are Evidence Objects.

Visual context should make the relationship clear.

Example:

Project A
↓
Incident #123
↓
Evidence
↓
Photo #4

Evidence components should communicate:

- Ownership / Association
- Local Save
- Upload Status
- Verification
- Failure / Retry

---

33. Draft Visual Language

Drafts are first-class Product objects.

The visual system should communicate:

Draft
↓
Resume

rather than implying:

Draft
↓
Restart

Draft components should preserve visible context wherever possible.

↓

API Contract
↓

---

43. Schema Boundary

The following rule remains active:

UI Requirement
≠
Database Schema Delta

A Design System requirement must never be treated as automatic justification for a migration.

A migration requires a real, independently proven schema delta.
