1. Gate Objective

P4.2 با هدف تعریف نظام رنگ و Semantic Tokenهای قابل استفاده در کل محصول GeoField انجام شد.

این Gate باید موارد زیر را مشخص و تثبیت کند:

- Primitive Color Palette
- Semantic Color Tokens
- Light Theme
- Dark Theme
- Interactive States
- Status States
- Offline / Sync / Verification States
- Draft / GNSS States
- Component-level Color Aliases
- Relationship بین Primitive و Semantic Tokens
- قواعد استفاده از رنگ در Web و Mobile
- قواعد استفاده از رنگ در RTL/LTR
- محدودیت‌های Accessibility و GIS Overlay
- مرز بین Design Baseline و Permanent Freeze

P4.2 یک Gate طراحی سیستم است و هیچ تغییر Backend، Database، API یا Migration ایجاد نمی‌کند.

15. Semantic Alias Mapping

Component-level tokens must reference semantic tokens rather than raw colors.

Button

button.primary.background
    → interactive.primary

button.primary.background.hover
    → interactive.primary.hover

button.primary.background.pressed
    → interactive.primary.pressed

button.primary.content
    → content.inverse

Input

input.background
    → surface.default

input.border
    → border.default

input.border.focus
    → border.focus

input.border.error
    → border.error

Card

card.background
    → surface.default

card.border
    → border.subtle

Badge

badge.success.background
    → status.success

This alias layer allows Components to change without changing the Primitive palette.

16. Color Usage Rules

16.1 Primary Color

Primary color is reserved for:

Primary Actions
Navigation Selection
Interactive Focus
Important Spatial Selection
Primary Links

It should not dominate the whole interface.

---

16.2 Green

Green represents positive operational semantics:

Success
Available
Verified
Completed
Healthy

Green must never be used as a generic decorative color when the state is not positive.

---

16.3 Amber

Amber represents:

Pending
Attention
Warning
Uncertain
Limited Availability
Needs Review

Amber is particularly important for the operational states of:

Offline
Sync
GNSS
Verification
Draft

---

16.4 Red

Red represents:

Failure
Critical Error
Unavailable
Dangerous Operational Condition

It should be used sparingly.

---

16.5 Neutral

Neutral colors carry most of the application structure:

Surfaces
Typography
Borders
Supporting UI
Secondary States

GeoField should remain structurally neutral with semantic color used for attention.

---

17. Offline Color Semantics

Offline mode is an Operating Mode and not an Error Screen.

Therefore:

offline.active
    ≠ error

offline.limited
    = constrained capability / attention

offline.unsupported
    = unavailable functionality

Visual treatment must preserve user confidence and avoid implying data loss merely because connectivity is absent.

---

18. Sync Color Semantics

Sync must remain distinct from Save.

The color system therefore supports:

sync.pending
sync.uploading
sync.success
sync.failed
sync.attention

These states must not be visually collapsed into a single “success/failure” status.

The system must preserve the conceptual distinction:

Saved Locally
    ≠
Uploaded
    ≠
Synced
    ≠
Verified

---

19. Verification Color Semantics

Verification represents trust/confirmation rather than merely transport success.

Therefore:

verification.pending
verification.verified
verification.failed
verification.required

are semantically independent from sync states.

---

20. GNSS Color Semantics

GNSS status uses color to communicate signal/position confidence:

Searching
    → blue

Available
    → green

Uncertain
    → amber

Unavailable
    → red

These colors must always be accompanied by clear text/icon semantics where the state is operationally important.

Color alone is not sufficient.

---

21. Accessibility Rule

Color must never be the only carrier of critical information.

Critical states must use a combination of:

Color
+
Icon / Shape
+
Text / Label
+
State change where appropriate

Examples:

Sync Failed
    = red + error icon + explicit text

GNSS Uncertain
    = amber + location/GNSS icon + explicit text

Verified
    = green + verification indicator + explicit text

Accessibility and contrast validation is a required follow-up activity.

---

22. GIS Overlay Constraint

GeoField is a GIS-oriented application.

UI colors may appear simultaneously with:

Raster Layers
Vector Layers
Satellite Imagery
Basemaps
Features
Routes
Boundaries
Heatmaps
Selections
Markers
Tracks

Therefore semantic UI colors must be validated against realistic GIS backgrounds.

Special validation is required for:

Selection
Primary Feature Highlight
Warning Feature
Critical Feature
GNSS Position
Sync / Status Overlay
Map Controls

GIS Overlay validation is not considered complete at P4.2.

---

23. Dark Mode Rule

Dark mode is not implemented by simply inverting light-mode colors.

Instead:

Light Theme
    and
Dark Theme

each have explicit semantic values.

The following must remain semantically stable across themes:

Success
Warning
Error
Info
Selected
Focus
Offline
Sync
Verification
GNSS

Only their visual representation changes.

---

24. RTL / LTR Compatibility

Color tokens are direction-independent.

No semantic token may depend on:

LTR
RTL
Persian
English

The same token names must work for:

fa
en

and future supported locales.

Direction-specific behavior belongs to layout and interaction systems, not the color system.

---

25. International / Country-Neutral Constraint

The color system does not encode country-specific identity.

No token may be named or semantically tied to:

Iran
Iranian
Khuzestan
National Colors
Government Colors
Country Flags

Product identity remains:

International
Country-Neutral
Localization-Aware

Persian is a supported UI language, not a product-identity constraint.

---

26. Mobile and Web Consistency

Web and Mobile must use the same semantic meaning.

For example:

status.error

must mean failure on both platforms.

However, Components may render differently:

Web → Badge / Table Cell / Banner

Mobile → Chip / Inline Status / Bottom Sheet

Therefore:

Same Semantics
≠
Identical Component Rendering

---

27. Map-Specific Color Constraints

The map is the primary spatial interaction surface.

Map-specific colors must distinguish at least:

Selected Feature
Current Location
User Track
Active Investigation
Warning Feature
Critical Feature
Operational State

The exact map palette remains subject to actual Map Engine selection and GIS overlay validation.

No map engine is frozen in P4.2.

---

28. Component Token Policy

Components should preferably consume:

Component Alias
    ↓
Semantic Token
    ↓
Primitive Token

rather than:

Component
    ↓
#2563EB

Hard-coded raw colors inside UI components are discouraged except where technically justified and documented.

---

29. Token Naming Rules

Naming follows semantic responsibility.

Preferred:

surface.default
content.primary
border.default
interactive.primary
status.error
sync.pending
verification.verified
gnss.available

Avoid:

blueButton
greenText
darkCard
iranBlue
redWarningButton

The latter creates visual coupling and makes future theme changes difficult.

---

30. Token Stability Rules

Token names should remain semantically stable even if values change.

Example:

status.success

may change from one green value to another after accessibility validation.

The Component API should not need to change.

This is a key purpose of semantic tokens.

---

31. Design Baseline vs Permanent Freeze

P4.2 establishes the current concrete color baseline.

It does not permanently freeze the brand palette.

Current policy:

Concrete Baseline = YES
Permanent Freeze   = NO

Values remain subject to validation in later Gates for:

Accessibility
Contrast
GIS Overlay
Map Readability
Cross-Platform Rendering
Dark Mode Validation
Real Component Usage

Any future change must be intentional, documented and reviewed.
